# 사내 MCP 실행 = CI 자동 검사 → goose 시험

스크립트: `node "${CLAUDE_PLUGIN_ROOT}/scripts/kitdev.mjs"`
(치환되지 않았으면 이 스킬의 Base directory 기준 `../../scripts/kitdev.mjs`)
`.kit/workspace.json` 이 없으면 먼저 `mcp-setup` 스킬을 쓴다.

## 규칙
- MCP 를 이 PC 에서 직접 띄우지 않는다. `python -m ...`, `goose` 를 직접 실행하지 않는다.
  - 시험은 항상 아래 `test` 로만 한다. 회사 정책상 통과한 코드만 샌드박스에서 돈다.
- CI 를 건너뛰는 방법(워크플로 수정·삭제, 강제 push)을 쓰지 않는다.
  - CI 가 틀렸다고 판단되면 사용자에게 알린다.

## 고리
1. 코드를 고친다.
   - MCP 계약: `kit-mcp.json` 의 `name`·`entry`·`egress`.
   - 의존성은 `requirements.txt` 에 `==` 로 고정한다.
   - 비밀값은 `kit-mcp.json` 의 `secrets` 에 환경 변수 이름만 적는다.
2. CI 를 돌린다.
   ```
   node "<스크립트>" ci -m "<무엇을 고쳤는지 한 줄>"
   ```
   - 실패하면 출력은 다음과 같다.
     - 단계 목록(✗ 표시가 실패 단계)
     - `KITCI-FAIL <단계>: <까닭>` 과 그 앞 로그
   - 그 까닭만 보고 코드를 고친 뒤 2를 다시 돌린다.
   - 같은 실패가 3번 넘게 되풀이되면 멈추고 사용자에게 상황을 말한다.
   - 내용이 같으면 스크립트가 지난 결과를 다시 쓴다. 같은 코드로 다시 돌릴 필요가 없다.
3. 통과하면 goose 로 시험한다.
   ```
   node "<스크립트>" test -t "<툴을 실제로 부르게 하는 질문>"
   ```
   - 질문은 고친 툴이 실제로 불리도록 구체적으로 쓴다.
   - goose 답과 툴 호출 결과를 보고 기대와 다르면 1로 돌아간다.
4. 사용자에게 보고한다. 통과한 커밋, 시험 질문, goose 가 부른 툴과 결과를 짧게 말한다.
