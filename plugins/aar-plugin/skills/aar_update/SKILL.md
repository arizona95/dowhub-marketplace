> 🚨 **폴링 금지(절대).** env·VM·페이지·API 상태를 짧은 간격으로 반복 조회하며 기다리지 마라 — 열어둔 탭이 12일간 콘솔을 1~2초마다 조회해
> env 가 "활동 중"으로 잡혀 자동 정지가 안 걸리고 하루 종일 과금된 실사고(2026-09-15). 기다림은 **한 번 조회 → 아직이면 적고 넘어감**.
> 불가피하면 **총 30분 제한, 간격은 분 단위**, 30분 안에 안 되면 ⛔ 사유 보고. 작업이 끝나면 **탭·브라우저·프로세스를 닫는다**(열어둔 화면 = 폴링).
> 🧭 **env 는 제품으로 찾는다** — `env("for_product", name=<제품>)` 로 그 제품에 연결된 env 와 (계정, 플랜) 세트를 받는다. 하나면 그것, 여럿이면 요청 문맥으로 고르고 모호하면 묻는다.
> `exists:false` 는 쓰지 않는다. stopped 면 `env("start", name)`. 연결된 env 가 없으면 추정하지 말고 `env("list")` 를 보여주고 묻는다 — 새로 만들지 않는다. 로그인은 사람이 한다(비밀번호를 묻거나 적지 않는다).
> 🔄 env 를 켜거나 끈 뒤에는 콘솔을 Ctrl+Shift+R(강력 새로고침) 하고 접속하라 — 옛 연결 때문에 화면이 안 뜨는 걸 env 고장으로 오판해 재시도(폴링)하지 마라.

# 변경점 중심 업데이트 (aar_update)

사용자 원문(2026-09-27): "전체 트리거 업데이트(예: 메뉴에 뭐가 추가되었는지 등)를 가지고, 뭘 업데이트해야 되는지를 스스로 판단하여 고치는 식 —
전체 업데이트를 루프로 도는 게 아니라 뭐가 달라졌는지 변경점을 종합해서 뭘 업데이트해야 되는지를 스스로 알아내서 업데이트하는 것.
업데이트 요약을 뽑아내는 과정과 업데이트를 뭘 할지 결정, 업데이트를 하는 루프 — 이렇게 두 개가 나뉜다.
aar_update 뒤에 지시가 붙으면 요약은 그걸로 하고, 그 지시로 업데이트를 뭘 할지 루프가 도는 것."

## 한눈에

```
/aar_update            ─▶ ① 신호 수집 ─▶ 업데이트 요약 ─┐
/aar_update <지시>     ─────────────────▶ 요약 = 지시 ──┤
                                                        ▼
                         ② 결정: 요약의 변경점마다 연결(Link)을 따라 영향 대상을 찾아 **작업 목록**
                                                        ▼
                         ③ 루프: 작업 하나씩 고침 → 고치다 새 변경이 생기면 목록에 추가 → 목록이 빌 때까지
                                                        ▼
                         기록: 요약·작업 목록·결과를 memory_note, update_targets 로 남은 due·낡은 묶음 확인
```

- 단계는 **두 덩어리**다: **(A) 요약·결정**(①②) 과 **(B) 업데이트 루프**(③). A 가 끝나 작업 목록이 확정되기 전에는 아무것도 고치지 않는다.
- 🚫 **전수 순회 금지.** 모든 트리·항목·보고서를 차례로 다시 찍지 않는다. 작업 목록에 없는 대상은 건드리지 않는다.
- 🚨 **새 표면(세션·이용 형태)·범위 변경도 업데이트다**(2026-10-17 사용자 "지금 이것도 CLI 추가가 업데이트잖아?"). 그 표면에 시나리오 실증이 많이 필요해도
  aar_review 로 **넘겨 버리지 않는다** — 점검표·작업 목록·루프는 이 스킬이 쥐고, 시나리오 실증(coverage_ledger·scenario_start·html_report)은 작업 목록의 한 종류로 넣는다.
  제품을 처음 리뷰할 때만 aar_review 로 전수.

## 업데이트 대상 — 계단식(폴더)으로 있다 = 제품 데이터 지도

사용자 원문(2026-10-17): "어떤 데이터가 전체적으로 있고 … 전체적인 걸 항상 생각을 해야 돼 이것만 고치고 다 했다고 하지 말고 … 새로 변화 중에 어디를 고쳐야 되는가를 약간 트리 형식으로 계속 이제 서칭을 한 다음에 이제 그 계획을 세우고 그거를 바꾸는 걸로".
아래 지도가 **②의 영향 탐색 순서**다 — 변경점마다 맨 위 가지부터 끝까지 내려가며 "닿나?"를 본다(연결로 안 잡히는 열·행 단위 데이터까지).

```
<제품>                                   (Product — 한 제품의 제품 DB 전부)
├─ 개요                                  (Product: 이름·실험 제약 constraints·환경 envs·계정 accounts · 전체 구성도 archify + 카드)
├─ 가정(판정 전제)                        (aar_core/assumptions/<제품>.json — scope 등 사용자 결정)
├─ 트리                                  (TreeNode — tree: menu · session · managed-settings · data-retention)
│   ├─ 노드 ─ 사진 세트(Annotation)
│   └─ session 잎 = **열·행 열쇠** ──┬─ 모니터링 표(MonitorFact — 세션 잎 × 항목 × 방법)
│                                    ├─ 네트워크 통제(NetControl 기능 × NetEffect 세션 칸)
│                                    └─ 세션 구성도(netmap_archify/<제품>/<slug> + 상세 Graph net_map)
├─ 관리자 추가설정 구조 그림               (settings_archify/<제품> + 상자 → managed-settings 노드)
├─ 메뉴 재현(MenuToy)                     (Source → MenuPage → MenuSlot → Item · ItemSpec · Locator · PopupSetting · Observation)
├─ 도구 통제                              (ToolEntity 실체(태그: 실행 위치·통신…) → ToolFact 사실 칸 — 맥락 when 포함)
├─ 브라우저                               (browser 태그 실체 → monitoring·url_block 칸)
├─ 체크리스트 판정                        (Assessment — 전역 문항 Criterion 에 대한 이 제품의 판정)
├─ 문서 카드                              (WebCard — 공식문서 URL)
├─ 질문 공백                              (QuestionGap open — 이 변화로 답이 생기는 것)
└─ 보고서                                 (Report — 시나리오별 버전, 블록이 노드·항목을 ReportRef 로 가리킨다 · 실험 보고서 탭은 판정 근거에서 도출)
```
대상끼리는 **연결 atom(Link)** 으로 이어져 있다 — 트리 노드 ↔ 메뉴 재현 항목 ↔ 보고서, 실체 ↔ 등록 경로 노드, 항목 ↔ 체크리스트 문항, 문서 카드 ↔ 문항.
그래서 한 대상이 바뀌면 **연결을 따라가면** 영향받는 대상이 나온다(`link("list", a)`). ②의 판단은 이 연결 그래프가 근거다.
어느 대상이 주기 추적 대상인지는 그 정의의 `update` 속성(주기·방법)이 진실이다 — `update_targets("list", product)`.

## ① 신호 수집 → 업데이트 요약  (지시가 붙으면 건너뛴다)
- 🔁 시작 때 반복 실수: AgentReview 저장소가 있는 PC 면 `AgentReviewPlugin/vmscreen/vms-audit recall`(지난 실행들에서 되풀이된 호출 낭비 — 이번에 피한다 · 없는 PC 면 건너뜀).

**신호** = "지난번 이후 무엇이 달라졌나"를 알려 주는 것. 전부 한 번씩만 모은다(반복 조회 금지):

| 신호 | 어디서 | 무엇을 알려 주나 |
|---|---|---|
| 주기가 된 대상 | `update_targets("list", product)` 의 due | 확인할 때가 된 트리 루트·수집 소스·문서 카드 |
| **낡은 데이터(노화)** | 같은 응답의 `stale` 묶음 · `freshness` 요약 — 아래 「노화 — 낡은 것부터 다시 본다」 | 마지막으로 확인한 지 91일 넘은 트리 노드·사진 화면·판정 칸(근거 오래됨)·보고서 줄·실체·기능·그래프·문서 카드·메뉴－웹 항목 · **죽은 링크** · 다시 봤더니 바뀜/사라짐(아직 안 고침) |
| 메뉴 변화 | `menutoy("collect", product, source, url=<env>)` → `collect_status` → `menutoy("sources", product)` / `reparse` 의 added·removed·changed | 메뉴 항목이 새로 생김·사라짐·값·문구 변경 |
| **메뉴 재현 ↔ 트리 어긋남** | 수집 뒤 `menutoy("drift", product)` — 아래 「메뉴 재현 ↔ 트리 루프」 | 어느 쪽이 뒤처졌나: 트리가 옛 모습(tree_behind) / 메뉴 재현이 못 따라옴(toy_behind) |
| 트리 변화 | `tree("changelog", tree_id, since=<지난 추적일>)` | 지난 추적 이후 트리 노드 +/−/~ |
| 문서 변화 | 문서 카드 URL 을 실제로 열고 `menutoy("web_check", product, url, html=<본문>)` → same·changed·unreachable | 공식문서(정책·가격·보안) 문구 변경 |
| 벤더 변경 공지 | 에이전트 센싱(aas) 기록·릴리스 노트(공식 URL 을 직접 열어 확인한 것만) | 새 기능·관리자 설정 추가·변경 |
| 화면 재관찰 | 트리 due 인 제품 루트를 내 브라우저로 훑어 **달라 보이는 지점만** 기록 | 새 메뉴·새 관리자 토글·기본값 변경·보존 정책 변경 |
| **답 못 한 질문(질문 공백)** | `question("gaps", product, status="open")` | 사람이 AI 에게 물었는데 자료가 모자라 답하지 못한 부분 — 그 주제를 채울 일. **신호가 이것뿐이어도 업데이트는 돈다** |

**업데이트 요약** — 신호를 한 장으로 종합한다. 변경점 하나 = 한 줄:
```
[변경점 id] 무엇이 · 어디서(제품·화면 경로) · 어떻게(추가/삭제/변경 — 전·후) · 근거(신호 출처: collect diff / changelog / web_check / 캡처 라벨)
예) C1 플러그인 탭 '+ 추가' 메뉴에 '마켓플레이스 추가' 항목 신설 · claude-app 사용자 지정 › 플러그인 · 추가 · reparse added itm_… / 캡처 upd-…-03
```
- 신호가 없으면(변경 0) → 요약 "변경 없음"으로 기록하고 끝낸다(②③ 없음).
- 추측으로 변경점을 만들지 않는다 — 신호에 없는 것은 요약에 없다.

## 노화 — 낡은 것부터 다시 본다 (2026-10-18)

사용자 원문(2026-10-18): "노화가 좀 많이 된 거가 대상이 … 쭉 봐가지고 새로 봤다 싶으면은 노화 상태를 계속 최신 상태로 유지해주고 … 1년 전 해놓은 실험에 의존하고 약간 이런 거는
좀 아닌 것 같아서" · "링크 … 그 메뉴가 없어지실 수도 있잖아 … 죽은 링크 처리".
데이터마다 **마지막으로 확인한 날**이 있다(규칙 한 곳 = 서버 `aar_core/freshness.py` — 신선 ≤30일 · 보통 ≤90 · 낡음 ≤180 · 오래됨 ≤365 · 1년 넘음). 낡음 이상이 업데이트 대상이다.
1. `update_targets("list", product)` 의 `stale` 묶음을 **위에서부터**(가장 오래 확인 안 한 묶음 → 그 안에서 가장 오래된 것) 작업 목록에 넣는다. 묶음마다 `how` 가 고치는 길이다.
2. 그 대상을 **실제로 다시 본다**(화면·문서·실험 — 캡처를 남긴다).
3. **같으면** 내용은 건드리지 않고 다시 본 사실을 남긴다:
   `update_targets("confirm", product, ref=<대상>, result="same", evidence=[이번 캡처 Evidence id 또는 보고서 블록], note=<무엇을 봤고 무엇이 같았나 — 완결 문장>, scope="subtree"(트리 노드 아래 전부를 훑었을 때)|"self", how="screen"|"doc"|"experiment"|"db")`
   → 확인한 날이 그 캡처 날로 새로 된다(옛 캡처로 '확인' 하면 나이는 그 옛 날 그대로다 — 이번에 찍은 것만).
4. **다르면** 기존 길로 고친다(트리 `update_tree` · 판정 `tool_gov fact_set` 등 새 근거 · 사진 재촬영 · 연결 `link`). 고치기 전에 본 것을 남기려면 `confirm(result="changed"|"gone")` —
   그 대상은 고칠 때까지 '다시 봤더니 바뀜 — 아직 안 고침' 묶음에 남는다.
5. 이미 확인 사실이 있는 것은 confirm 으로 적지 않는다(서버가 거부하고 길을 알려 준다): 문서 카드 = `menutoy web_check` · 메뉴－웹 항목·소스 = `menutoy collect`(succeeded).
6. **실험 신빙도** — 판정 칸의 근거 나이는 칸 옆 정보다. 🚫 낡았다고 판정 값을 바꾸지 마라(O 를 ? 로 내리기 금지). 근거 실험을 다시 돌려 같으면 confirm(근거 = 새 블록),
   다르면 새 근거로 `fact_set`. 1년 넘은 근거에만 기댄 칸이 있으면 종합 보고서(S3) 발행 응답에 `freshness_warning` 이 칸 목록으로 온다 — 결과 보고에 그 수를 적는다(발행 거부는 아니다).
7. **죽은 링크**(한쪽 끝이 최신 트리·최신 메뉴 재현·최신 보고서에 없음 — 화면에 '죽은 링크' 로 보인다): 묶음의 `candidates`(같은 트리·같은 이름의 살아 있는 노드)는 **후보일 뿐**이다.
   화면으로 같은 대상임을 확인한 것만 `link("add", …)` 로 다시 잇고 옛 연결은 `link("remove", …, reason)`. 이름만 같다고 잇지 않는다. 확인할 수 없으면 끊기만 하고 까닭을 적는다.

## `/aar_update <지시>` — 지시가 요약이다
- 예: `/aar_update 스킬 공유 설정 설명이 바뀌었대` · `/aar_update 플러그인에 마켓플레이스 추가 메뉴가 생겼어`
- ① 신호 수집을 **건너뛰고**, 지시를 요약의 변경점으로 옮긴다(지시 하나가 여러 변경점이면 나눈다). 지시가 가리키는 화면을 **한 번 확인**해 전·후를 캡처로 남긴다(지시가 사실과 다르면 그 사실을 보고하고 그 변경점은 뺀다).
- 트리 뷰어에서 보고서가 비어 있는 항목의 "📋 복사" 는 `/aar_update <트리> <노드경로> …` 한 줄을 준다 — 그 노드 하나가 변경점이다(옛 `aar_menu` 에서 옮김):
  `has_report` — **이미 보고서가 붙어 있으면 그렇다고 말하고 멈춰라.** 화면에서 ①기능 ②설정 방법과 현재값 ③보안 권고 ④위험 을 채우고,
  🚨 **블록에 `items`(그 노드의 id — `tree("get")` 결과의 id)를 빼면 트리에 안 붙는다** — 빈칸이 그대로 남는다. **한 항목만** — 옆 항목까지 번지지 마라.
- ②③ 은 아래와 똑같다.

## 메뉴 재현 ↔ 트리 루프 (어긋남 → 뒤처진 쪽 고침)

사용자 원문(2026-09-29): "메뉴 토이에서 뭔가 뒤쳐지는 게 있으면 그거를 기반으로 아 여기 업데이트를 해야겠다라는 생각을 가지고 메뉴 트리를 업데이트 하던가
혹은 그 반대도 될 수 있도록 업데이트 루프를 돌아야" · "꼭 그렇게 다 이어질 필요는 없고".
메뉴 재현 = 실제 화면을 크롤러가 긁은 것, 메뉴 트리 = 사람이 정리한 구조. 둘은 **서로의 검산**이다 — 한쪽이 앞서 있으면 다른 쪽을 고친다.
노드↔항목 연결은 어긋남을 찾는 수단일 뿐이다: **모든 칸을 트리에 두거나 전부 이을 필요는 없다**(플랫폼 설정처럼 트리에 화면이 없는 칸은 그대로).

`menutoy("drift", product)` 가 후보를 준다(각 줄에 근거·hint). **후보는 판정이 아니다** — 화면으로 확인하고 고친다.

| direction · kind | 뜻 | 확인 | 고침 |
|---|---|---|---|
| tree_behind · `item_gone` | 트리 노드가 이어진 칸이 화면에서 사라짐(successors = 이름·설명이 같은 새 칸) | 그 화면을 열어 칸이 없어졌는지·옮겨졌는지 | 옮겨짐 → 연결을 새 칸으로(`link` replace) + 트리 노드를 새 위치로 · 없어짐 → 트리에서 내림 |
| tree_behind · `page_mismatch` | 노드의 칸이 트리 화면(Cowork 등)과 다른 페이지에 있음 | 화면에서 그 설정이 실제로 어느 페이지에 있나 · 옛 자리에 포인터 행('…로 이동되었습니다 [기능에서 관리]')이 남았나 | 노드를 새 페이지 가지로 **옮긴다** — `update_tree(새 부모, patch=[{"name", "move_from": [옛 경로]}])`(같은 id 라 연결·보고서·사진이 따라온다. 지우고 새로 만들지 마라). 옛 자리에 포인터 행이 있으면 그 자리에 포인터 노드를 새로 두고 포인터 칸과 잇는다 |
| tree_behind · `new_on_screen` | 트리 마지막 변경 뒤 화면에 새로 생긴 칸(안 이어짐) | 메뉴로서 트리에 둘 만한가(탭·필터·목록 행은 대개 아님) | 둘 만하면 노드 추가 + 연결, 아니면 둔다 |
| toy_behind · `nav_uncollected` | 사이트 사이드바에 있는데 수집 목록 밖인 페이지 | 그 페이지가 실제로 열리나·탭이 있나(탭마다 `?tab=` 주소를 주소창으로 확인) | `source_set` urls 에 넣고 수집 |
| toy_behind · `tree_page_missing` | 트리의 화면 자리인데 메뉴 재현에 그 페이지가 없음 | 사이트에 그 화면이 아직 있나 | 있으면 URL 확인 → 수집 목록 + 수집 · 없어졌으면 트리에서 내림 |
| toy_behind · `node_after_collect` | 마지막 수집 뒤 트리에 생긴 노드(안 이어짐) | 그 화면을 다시 수집해도 그 칸이 없나 | 재수집 → 그래도 없으면 파서가 그 칸을 못 읽는 것(파서 수정 → `reparse`) |

순서: 수집(succeeded) → `drift` → 후보마다 화면 확인 → 뒤처진 쪽 고침 → **다시 `drift` 로 그 후보가 사라졌는지 확인**(고친 뒤 실측, 부정 결론 금지)
→ 끝에 `menutoy("drift_done", product, note=<고친 것·그대로 둔 것과 까닭, 완결 문장>)` — 다음 실행의 new_on_screen 기준 시각이 된다(안 남기면 다음에 같은 새 칸을 또 본다).
- 🚨 보고서 ↔ 트리 연결은 노드 id(Link) 라 `move_from` 으로 옮기면 따라온다. **지우고 새로 만들면** 보고서·메뉴 재현 항목·실체 연결이 끊긴다 — 태그를 버리는 재빌드 금지.
- 칸 값이 화면과 달라 보이면(값 없음·충돌) 수집 env 기록부터 본다 — 지운 env 의 옛 관측은 살아 있는 관측이 있으면 현재값에서 빠진다.
- 관리자 콘솔은 관리자 계정 PC(예 admin-window-pc)에서 수집한다: `menutoy("collect", …, meta={"component": "admin-window-pc"})`.
- 한 실행에서 같은 노드·칸은 한 번만 고친다. 확인했지만 고칠 것이 없던 후보(포인터 행·트리에 안 둘 칸)는 기록에 "그대로 — 이유" 로 남긴다.

## ② 결정 — 무엇을 업데이트할지 (작업 목록)

변경점마다 **닿는 대상을 연결로 찾아** 작업을 만든다. 순서:
0. **영향 트리 탐색(점검표)** — 위 「제품 데이터 지도」의 **모든 가지**를 위에서부터 내려가며 변경점마다 `바꿀 것 / 해당없음(까닭) / 막힘(까닭)` 을 적는다.
   DB 를 실제로 조회해 지금 상태(개수·빈 칸·지워진 노드)를 적고 짐작으로 채우지 않는다. 연결(Link)로 안 잡히는 것 — 세션 잎이 열쇠인 모니터링 행·네트워크 통제 열·세션 그림, 가정 scope, 개요 구성도 상자 — 를 특히 본다.
1. **그 변경점의 자리(앵커)** — 변경점이 가리키는 트리 노드·메뉴 재현 항목·문서 카드·실체를 찾는다(없으면 "새로 생긴 것" — 앵커 = 부모 노드).
2. **연결 따라가기** — `link("list", <앵커>)` 로 이어진 대상(보고서·항목·실체·문항)을 모으고, 보고서는 그 블록이 가리키는 노드가 앵커면 대상이다.
3. **영향 규칙**(해당하는 것만 작업으로):

| 변경점 종류 | 작업 |
|---|---|
| 메뉴·설정 노드 추가/삭제/문구 변경 | 트리 `update_tree`(그 앵커만) · 연결된 메뉴 재현 항목 갱신 · 연결 추가/끊기 |
| `drift` 후보(메뉴 재현 ↔ 트리 어긋남) | 위 「메뉴 재현 ↔ 트리 루프」 표의 고침 — 뒤처진 쪽만(트리 또는 수집 목록·파서) |
| 새 관리자 토글·기본값 변경 | 위 + 도구 통제: 그 토글이 통제하는 실체의 사실 칸 재실증(S1-tool-control) · 체크리스트 판정 재확인 |
| 새 등록 입구(스킬·MCP·플러그인·에이전트를 올리는 곳) | 도구 통제 실체 추가(등록 예제·steps·등록 경로 연결) + 그 실체의 사실 칸 실증 |
| 공식문서 changed | 문서 카드 `web_add` 설명 고침 · 그 카드에 이어진 문항 판정·도구 통제 사실(문서가 근거인 칸) 재확인 |
| 보존·로그 정책 변경 | data-retention 트리 · 해당 시나리오 보고서 |
| 질문 공백(open) | 공백 글이 말하는 자료를 채운다 — 화면·문서를 실제로 열어 캡처 → 트리 노드·판정 칸·데이터 보존 노드·보고서 중 그 질문에 답이 될 곳에 넣는다. 다 채우면 `question("gap_close", id=…, status="done", resolution=<무엇을 어디에 채웠나 — 완결 문장>, reports=["rpt_…@n"])`. 제품 범위 밖이거나 채울 수 없는 까닭이 확정되면 `status="dropped"` + 까닭(완결 문장). 추측으로 닫지 않는다 — 채우지 못했으면 열어 두고 결과에 '막힘(사유)' |
| **새 세션(이용 형태)·표면 추가 / 범위 변경** | 가정 scope · 세션 트리 잎(지워진 노드면 되살림 — 새로 만들지 않는다) · 모니터링 표 그 행 실증 · 네트워크 통제 그 열 판정 · 전체 구성도 상자·선 + 그 세션 그림 · 도구 통제 실체(그 표면의 등록 입구·실행 위치 태그)·사실 칸 · 브라우저 실체(그 표면의 브라우저 도구) · 메뉴 트리(그 표면의 화면) · 관리자 추가설정(그 표면이 읽는 설정) · 데이터 보존(그 표면의 저장 지점) · 체크리스트 연결 · 그 표면 질문 공백 · 그 표면 시나리오 원장(coverage_ledger)의 보고서 |
| 위 대상 중 보고서의 블록이 가리키는 것이 바뀜 | 그 **시나리오만** 재실증해 보고서 새 버전(`html_report`) — kind=periodic 보고서는 반드시, 나머지는 바뀐 게 있을 때만 |

4. **작업 목록** — `[작업 id] 대상(종류·id/주소) · 할 일 · 이 작업을 부른 변경점 id · 선행 작업`. 같은 대상은 한 작업으로 합친다. 선행 관계(예: 트리 노드를 먼저 만들어야 실체를 이을 수 있음)를 적는다.
5. 🚫 목록에 없는 대상은 ③ 에서 건드리지 않는다. 변화 없는 시나리오·항목은 재캡처하지 않는다.
6. 🗣️ **점검표·작업 목록을 사용자에게 대화로 보여 준다**(표 — 데이터 화면 · 지금 상태 · 할 일). 만들어 두고 말하지 않으면 사용자는 모른다(2026-10-17 "체크하고 리스트 올렸는데 나한테 말을 안한 건가?"). 보여 준 뒤 ③.

## ③ 업데이트 루프

작업 목록을 선행 순서대로 하나씩:
- **트리** — 바뀐 앵커에만 `update_tree(tree_id, node_path=[앵커], patch=[그 아래 현재])`. 삭제 판정은 앵커 서브트리 안에서만. 사진이 필요하면 `annotate_shot`·`shot_set`.
- **메뉴 재현** — 수집은 `menutoy("collect", …)` → `menutoy("collect_status", key=<job>, at="80")`(서버가 80초 대기) **최대 25번(≈30분)** 까지만(옛 `aar_menutoy` 에서 옮김). VM 의 브라우저에 그 SaaS 가 **로그인돼 있어야** 한다(안 돼 있으면 ⛔ 사유: 로그인은 사용자 몫). 수집 중엔 VM 화면을 건드리지 마라(키 입력이 섞인다).
  파싱 오류면 `menutoy("source_get", product, source)` 로 파서·raw 를 보고 **재수집 없이** 고친다 — 행 `k`(키)는 **화면 위치가 아니라 의미**로 안정되게(키가 바뀌면 diff 가 전부 +/− 로 보이고 체크리스트 연결이 끊긴다) → `source_set(parser=…)` → `reparse`. 항목 판정·팝업·문서 근거는 `menutoy`(`checklist_set`·`popup_set`·`web_add`). 새 제품 toy 는 `menutoy("toys")` 의 sources[].hosts 로 같은 SaaS 를 찾아 갱신(어느 toy 에도 없을 때만 새로).
- **도구 통제** — 절차 정본 = S1-tool-control 지시문. 실체 `tool_gov("entity_add"|"entity_edit")`, 사실 `tool_gov("fact_set", …, evidence=[캡처 블록], reason=완결 문장, actor)`. 판정 O/X/-/? 만(부분 판정 금지 — 애매하면 경로·범위별로 나눈다), 입구 없으면 '-', 관리자가 통제를 바꾸면 멤버 앱 새로고침·재시작 뒤 확인, 원복 5단계.
- **연결** — 같은 대상임을 화면으로 확인한 것만 `link("add", a, b, note)`, 사라진 대상과의 연결은 `link("remove", a, b, reason)`.
- **보고서** — `scenario_start` → 라이브 캡처 → `html_report`(블록 `items=[노드·항목 id]`). 보고서는 바뀐 것의 요약만(메뉴 전체 나열 금지).
- **번짐** — 고치다가 새 변경이 드러나면(예: 트리 노드를 고쳤더니 연결된 실체의 등록 경로가 바뀜) 변경점으로 요약에 추가하고 ② 규칙으로 작업을 만들어 목록 끝에 붙인다. 같은 대상이 두 번 들어오면 합친다(무한 루프 방지 — 한 대상은 한 실행에 한 번).
- 작업마다 결과를 `완료 / 막힘(사유 — 예: 로그인 필요) / 변화 없음(확인만)` 으로 적는다.

## 끝내기 전 — 완성 기준 검증(2026-10-12)
- ② 0 의 점검표 **모든 줄**이 `반영(근거 — 커밋·보고서 rev·판정 칸) / 해당없음 / 막힘` 으로 닫혔는지 먼저 본다. 열린 줄이 있으면 완료가 아니다(완성 기준 RC-23).
- "완료"라고 말하기 전에 독립 검증 서브에이전트 `aar-reviewer` 를 부른다 — 프롬프트에 제품·이번 세션들·작업 목록·닫은/남긴 질문 공백을 넘긴다.
  aar-reviewer 는 `list_guidance('완성기준')`(사용자 피드백으로 쌓인 리뷰 완성 기준 RC 전부)을 하나씩 본다. FAIL 이 오면 그 작업으로 돌아가 고치고 다시 부른다(PASS 까지).
- 이번 실행 중 사용자가 결과물이 어때야 하는지 새로 지적했으면, 끝내기 전에 그 지적을 완성 기준에 더한다(`/aar_fix` 의 '완성 기준 쌓기').

## 기록
- 호출 이력 자기점검(AgentReview 저장소가 있는 PC 만): 끝나면 `AgentReviewPlugin/vmscreen/vms-audit --self`(서브에이전트마다 `-a <agentId>`) — 위반·토큰 요약을 결과 보고에 그대로 붙인다(위반은 개선 접수함으로 — 다음 `recall` 근거).
- 작업 중이나 끝에 실수·반복 실수·개선 방향이 보이면 보고서 끝에 쓰는 것과 별개로 `harness("improve", kind=token|accuracy|procedure|tool|instruction, text=<한두 문장>, where=<고칠 곳>)` 로 보낸다(MCP 가 없으면 AgentReview 저장소에서 `python -m aar_core.harness improve --kind … --text "…"`) — 같은 내용은 횟수가 쌓여 반복 실수가 드러난다. 끝내기 전 게이트는 aar-reviewer 가 `harness("gate")` 로 회차를 남긴다.
- `memory_note(kind='note')` — 업데이트 요약(변경점 목록) · 작업 목록 · 작업별 결과 · 막힌 것. 다음 실행이 이어받는다.
- 끝에 `update_targets("list", product)` 를 다시 불러 due 와 `stale` 묶음(낡음 이상·죽은 링크·아직 안 고침)이 남아 있으면 묶음마다 수와 사유를 보고한다(마지막 갱신 시각은 자료에서 읽힌다).
- 갱신 완료로 세는 것 = succeeded 로 끝난 수집 · web_check same|changed · 트리 커밋 · 다시 본 사실(confirm same) · 발행된 보고서 버전 · 닫힌 질문 공백(done·dropped). 시작만 한 수집·partial·failed 는 완료가 아니다.
- 남은 열린 질문 공백(`question("gaps", product, status="open")`)의 수와 까닭을 결과에 적는다.

## 절대 규칙
- off-screen 금지 — 내가 직접 열어 본 것만(추측 노드·추측 변경점 금지). 캡처는 내 화면을 떠서 /api/v1/evidence 로 POST.
- 로그인 뒤 화면이 로그인 벽이면 blocked + 사유, 사용자에게 요청(비밀번호 입력 금지).
- 신선도 = 내용(md5), mtime 아님. 갱신 보고서도 이번 라이브 캡처만. 노화(확인한 날)는 서버가 계산한다 — 날 수를 손으로 세거나 판정 값을 나이로 바꾸지 않는다.
- 새 추적 대상 추가(`update_targets("set"|"set_product")`)는 사용자가 시킨 때만.
