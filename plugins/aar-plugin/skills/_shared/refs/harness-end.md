# 하네스 끝 단계 — 이번 실행에서 배운 걸 규범에 박기 (aar_review · aar_update · aar_feedback 공통)

사용자 원문(2026-10-23): "aar fix 는 버리자 (이건 자동으로 update review 이런거 찍을때 알잘딱갈센으로 돌아가게끔 하네스에 두는걸로)"

옛 `/aar_fix` 가 하던 일이다. 세 스킬이 **끝날 때마다(완료 보고 직전) 따로 부르지 않아도 이 단계를 돈다.** 고칠 것이 없으면 결과에
"하네스 끝 단계: 고칠 것 없음" 한 줄로 끝난다.
읽기: MCP `skill("get", "_shared/refs/harness-end.md")` · 플러그인 폴더에선 `skills/_shared/refs/harness-end.md`.

🚨 **규범 쓰기·읽기는 전부 MCP 툴로**(`edit_guidance`·`scenario("edit", …)`·`list_guidance`·`memory_recall`) — 플러그인은 클라이언트 PC 에서 돌고
AAR 로의 통로는 원격 MCP 뿐이다. `공통수칙.md` 같은 repo 파일을 Read/Edit 하려 하지 마라(그 PC 엔 없다). 규범의 정본은 **guidance 스토어**다.

## 1) 읽기 — 이 대화 + 개선 접수함
- **이 대화를 위로 훑어** 사용자가 지적·추궁한 지점("왜 이렇게 안 했어?", "이건 이렇게 하랬잖아")을 **전부** 뽑는다(마지막 것만 보지 마라). 지적마다:
  - **(a) 내가 무엇을 했나** — 잘못됐다고 지적된 실제 행동/판단(대화의 그 대목).
  - **(b) 사용자가 무엇을 바랐나** — 옳은 행동. 사용자가 명시적으로 말한 것만(안 한 말을 지어내 규칙화 금지).
  - **(c) 왜 어긋났나** — 어느 규범이 그렇게 시켰나, 아무 규범도 안 막았나. 확인은 `list_guidance()`(각 `list_guidance(name)` 본문)·`memory_recall(관련어)` 로.
- **개선 접수함** — `harness("digest")`(열린 개선 — 종류별 반복·낭비) · AgentReview 저장소가 있는 PC 면 `AgentReviewPlugin/vmscreen/vms-audit recall`(지난 실행들에서 3번 이상 되풀이된 실수 · 없는 PC 면 건너뜀).
- 지적도 반복 실수도 없으면 7) 만 하고 끝낸다.

## 2) 완성 기준 쌓기 — 결과물이 "어때야 완성인지"에 대한 지적이면(2026-10-12)
사용자 원문: "그 전체 이제 너가 일을 다 했다고 하는 이 조건 … 베리파이어 … 여기에 내가 했던 이 피드백 같은 거를 계속 이렇게 업데이트를 해가지고 … 내 피드백 기반으로 계속 쌓아줬으면 좋겠어".
- 지적이 **결과물의 모양·내용**(보고서·판정 칸·트리·구성도·업데이트가 이래야 한다)에 관한 것이면, 규범(3~4)과 별도로 **리뷰 완성 기준**에 넣는다 — 독립 검증자 `aar-reviewer` 가 다음부터 이 기준으로 FAIL 을 낸다.
- 먼저 `list_guidance('완성기준')` 로 본문 전체를 읽는다. 같은 뜻의 기준(RC-NN)이 있으면 새로 쌓지 말고 `edit_guidance('완성기준', old=…, new=…)` 로 그 기준의 원문 줄에 날짜·원문을 덧붙이고 검사 문장을 고친다.
  없으면 `edit_guidance('완성기준', append=…)` 로 다음 번호를 붙인다. 모양(문서 맨 위 '쓰는 법' 그대로):
  `## RC-NN 제목` / `- 원문(YYYY-MM-DD): "사용자 말 그대로"` / `- 검사: 무엇을 열어 무엇이면 FAIL 인지(제품 이름·좌표 같은 1회성 값 없이)` / `- 대상: 보고서|판정 칸|트리|구성도|업데이트|전체`
- 원문은 **대화에 있는 사용자 말 그대로** — 요약·재구성 금지. 대화에서 원문을 찾지 못하면 그 기준은 쓰지 않는다.
- 과정(작업 방식)에 관한 지적(묻지 말고 해라 · 폴링 금지 등)은 완성 기준이 아니라 규범(3~4)으로 간다.

## 3) 일반화 — 통찰력 있게 · 제품 무관하게 · 최대한 간단히
그 실패를 "같은 상황이 또 오면 막는" **규칙 한 줄**로 만든다:
- **통찰력 있게** — 표면(이번 그 화면·그 버튼)이 아니라 **밑에 깔린 원리**를 짚어라. "왜 그렇게 판단했나"를
  한 겹 파고들어 그 부류의 실수를 통째로 막는 규칙으로.
- **이 SaaS/제품에 국한하지 마라** — 이번 대상에만 맞는 하드코딩 금지. 어떤 제품을
  리뷰해도 통하는 표현으로(제품 고유값은 예시로만, 규칙 본문은 일반형).
- **최대한 간단히** — 재발을 막는 **가장 짧은 문장**. 장황한 배경·중복 수식 금지. 너무 좁게('이 파일만')도
  너무 넓게('전부 금지')도 아니게.

## 4) 어디에 박을지 정한다 (MCP 로 쓰기)
성격에 맞는 곳 하나:
- **행동 규범 전반**(증거·날조금지·스코프·off-screen 등) → `edit_guidance(name, ...)` — 해당 가이드에.
  없으면 새 이름으로 생성. 이게 기본값이다.
- **특정 시나리오에서만** → `scenario("edit", id, append=...)` 로 그 시나리오 instruction 에.
- guidance/scenario 어디에도 안 맞고 **플러그인 스킬 자체(SKILL.md)** 를 고쳐야 하면 → 클라이언트에선 못 고친다.
  그 변경안을 **표로 정리해 사용자(메인테이너)에게 보고**하고 repo 에서 반영하도록 한다.

> 🚫 **"내 기억/메모리에 저장" 으로 갈음하지 마라.** 규범은 **다음에 그 일을 할 에이전트가 읽는 곳**(guidance·시나리오
> 지시)에 있어야 효력이 있다. 내 개인 메모리는 나만 읽으므로 거기 넣는 건 아무것도 고치지 않은 것과 같다.
> 🚫 특정 대상 제품 전용 절차를 **도구·환경 코드에 박는 것**도 금지 — 이 도구는 아무 SaaS나 리뷰한다.

🚨 **넣기 전에 "이미 있나" 부터 확인한다** — `list_guidance(name)` 본문을 실제로 읽어 **같은 규칙이 이미 있는지 검색**하라.
이미 있으면 신규로 넣지 말고 **그 문구를 보강**하거나 그대로 둔다(실사고: 이미 있는 규칙을 신규인 양 또 제안).
🚨 **같은 지적이 반복된 것이면**(이 대화·과거에 여러 번 지적 · 접수함에서 횟수가 쌓인 것) 그건 규범 위치가 약한 것이다 — 더 **상위·앞쪽 규범**(공통수칙 등)으로 올려 박는다.

새 규칙을 넣기 전에 `list_guidance()` 전체를 훑어:
- **중복 제거** — 같은 규칙이 여러 가이드에 흩어져 있으면 하나로 모으고 나머지는 뺀다(`edit_guidance` old→"" 또는 replace).
- **상반 정리** — 이번 지적과 **반대로 지시하는** 기존 문구가 있으면 그게 이번 실수의 원인일 수 있다. 근거를
  대고 고치거나 뺀다(그냥 새 규칙만 얹으면 두 지시가 충돌해 또 헷갈린다).
- **다듬기** — 근처의 애매/노후 문구를 최소로 손본다. 단, **이 대화와 무관한 대수술 금지** — 관련된 것만.

## 5) 반영
- 규칙 추가·문구 보강은 `edit_guidance`/`scenario("edit", …)` 로 바로 반영한다(자동 단계 — 묻지 않는다).
- **큰 변경·삭제·재배치**는 durable 규범이라 함부로 안 쓴다 — **무엇을 → 무엇으로 + 근거(대화의 어느 대목)** 를 표로 먼저 보여주고 **사용자 확인 뒤** 반영한다.

## 6) 검증 + 대전제 감사 (`aar-compounder` 서브에이전트) — 이 단계에서 규범을 고쳤을 때 필수
- 고친 뒤 `list_guidance()` 를 다시 읽어 (a) 지적이 실제로 막히는지, (b) 새 모순을 안 만들었는지 확인.
- 그다음 **`aar-compounder` 를 부른다** — `Task(subagent_type="aar-compounder", …)`. 전술(이 대화→특정 수정)을 넘어 **가이드 코퍼스 전체의 대 전제**를 독립 감사한다:
  ① 특정 SaaS 치우침 잔존 ② 타겟 정확성(정확히 그 대상인지 되묻게 하나) ③ 중복·장황(→간결) ④ 통찰(원리 vs 하드코딩) ⑤ 방향 일관성(모순 없나) ⑥ **도구 실재성** — 없어진 함수를 부르라고 적혀 있나(툴이 바뀌면 글은 안 따라간다).
- `aar-compounder` 가 낸 결함목록은 **대전제 위반**이다. 그걸 `edit_guidance`/`scenario("edit", …)` 로 반영하고(큰 변경은 5) 의 확인 게이트), **다시 `aar-compounder` 를 불러 `PASS` 날 때까지** 반복한다. (compounder 는 읽기전용이라 스스로 안 고친다 — 반영은 이 단계가.)
- 결과에 바꾼 것을 표로 보고: **어느 가이드 / 무엇→무엇 / 이 대화의 어느 근거** · compounder PASS.

## 7) 기록
- 지적·반복 실수·개선 방향마다 `harness("improve", kind=token|accuracy|procedure|tool|instruction, text=<한두 문장>, where=<고칠 곳>)` 로 보낸다(MCP 가 없으면 AgentReview 저장소에서 `python -m aar_core.harness improve --kind … --text "…"`) — 같은 내용은 횟수가 쌓여 반복 실수가 드러난다.

## 절대 규칙
- **로컬 파일 금지** — 모든 규범 읽기·쓰기는 MCP 툴(`edit_guidance`·`scenario("edit", …)`·`list_guidance`·`memory_recall`). repo 경로(`공통수칙.md`·`SKILL.md`·`agent_memory.jsonl`)를 열려 하지 마라.
- **대화에 실제 있은 것만 근거** — 사용자가 안 한 말을 지어내 규칙화 금지.
- **간단·제품무관·통찰** 3원칙을 어긴 규칙은 넣지 마라.
- 원본 함부로 삭제 금지, 큰 변경의 확인 게이트 건너뛰기 금지. 이 단계 자신도 점검 대상이다.
